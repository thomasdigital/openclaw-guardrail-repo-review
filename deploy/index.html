Why not just install one?

The Subtraction Doctrine says no

Our own rule: no new gate without a retirement plan, and extend an existing gate before spawning a new process. A 7,200-line plugin or a standing daemon does the opposite — more code, more processes, more to break, and no off-ramp.

The security tool is the biggest risk

ClawGuard wants the deepest access of the three — it disables our real tools, rewrites config, and runs a daemon that can touch everything. With 5 commits and no audit trail, installing an unvetted high-privilege interceptor is itself an attack surface. A security tool earns more scrutiny, not a pass.

The prompt contract (source of truth)

Per your ask, the decision is codified into a durable contract so future sessions don't re-litigate this. It lives at ~/projects/openclaw-guardrail-repo-review/CONTRACT.md and governs how OpenClaw evaluates any external guardrail framework, not just these three. It was itself red-teamed by Codex.

The rule, in one breath: For any external guardrail repo — (1) grep our fabric first; if we already do it, reject adoption. (2) A new process needs a retirement plan and must prove no existing gate can be extended. (3) Anything that intercepts tools or runs a daemon must pass an audit — a low-commit high-privilege interceptor is an automatic no. (4) If ours is genuinely weaker, re-build the idea natively, never install the foreign code. (5) Even a rejected repo can still serve as a benchmark. Default posture: adopt none.
